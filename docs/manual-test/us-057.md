# US-057 — Guía de prueba manual (navegador)

**Rama**: `feature/E9-US-057-chatpanel`
**Alcance**: markdown sanitizado, tool cards colapsables, persistencia de historial, retry+backoff del SSE, envío de `locale` al `/chat`.

> Requiere backend `/chat` corriendo (`uvicorn backend.app.main:app --port 8000`) y `pnpm dev` (Nuxt :3000).
> NOTA BLOQUEANTE: el backend `ChatRequest` aún tiene `extra="forbid"` y NO declara `locale`. Hasta que se aplique el cambio backend pendiente, todo `/chat` real responderá **422** (el frontend ya envía `locale` en el body). Los flujos 2–5 con backend real fallarán por esto; usar mock SSE o el backend parcheado para validarlos.

## Prep
```
cd backend && poetry run uvicorn backend.app.main:app --reload --port 8000
cd frontend && pnpm dev
```
Abrir http://localhost:3000 (default it). Para cambiar idioma usar el prefijo de ruta: `/es`, `/en`.

---

## Flujo 1 — Chat trilingüe (it / es / en)
1. Navegar a `/` (it), `/es`, `/en`.
2. Verificar que las etiquetas del chat se traducen: encabezado de turno (`Tu`/`Tú`/`You`, `Assistente`/`Asistente`/`Assistant`), tool cards (`Input`/`Entrada`, `Output`/`Salida`, `Mostra i dettagli`/`Ver detalle`/`View details`).
3. En DevTools → Network, enviar un mensaje y abrir el request a `/chat`; confirmar en el payload `"locale": "it" | "es" | "en"` según la ruta activa.

**Esperado**: 0 strings hardcodeados; el `locale` del body coincide con el idioma de la URL.

## Flujo 2 — Markdown en vivo (tablas / código)
1. En cualquier idioma, pedir al asistente una respuesta con tabla y bloque de código (p. ej. "muéstrame una tabla de parcelas y una consulta SQL").
2. Observar el turno del asistente mientras hace streaming.

**Esperado**:
- Una tabla GFM se renderiza como `<table>` con bordes (estilo `.markdown-body`).
- Un fence ```` ```sql ```` se renderiza como `<pre><code>` con scroll horizontal.
- Los links son clicables (`target` seguro, sin `javascript:`).
- Funciona en dark mode (links `agro-400`, bordes por token).

## Flujo 3 — XSS (seguridad real)
1. Forzar que el asistente devuelva markdown con `<script>alert('xss')</script>`, `<img src=x onerror=alert(1)>` y `[x](javascript:alert(1))` (o inyectar vía un turno mock).

**Esperado**: NINGÚN `alert` se dispara; el `<script>` no aparece en el DOM, el `<img>` queda sin `onerror`, el link pierde el esquema `javascript:`. Verificado automáticamente: `renderMarkdown` pasa por `marked` → `isomorphic-dompurify` antes de `v-html`, y una sonda de ejecución real (innerHTML en jsdom) confirma que el script NO ejecuta.

## Flujo 4 — Tool card expand (JSON input/output)
1. Hacer una pregunta que dispare una tool (p. ej. listar parcelas de un AOI dibujado).
2. Mientras corre: el card muestra spinner + estado `en curso`/`running` (icono, no solo color).
3. Al resolver: estado `completado`/`done`, summary de una línea.
4. Click/Enter/Space sobre el `<summary>` → expande mostrando `Input` (args JSON) y `Output` (result JSON formateado).

**Esperado**: toggle por teclado (native `<details>`), foco visible (`focus-visible:ring`), chevron rota (respeta `prefers-reduced-motion`), JSON con indentado de 2 espacios; output vacío muestra el estado en cursiva.

## Flujo 5 — Reload persiste
1. Mantener una conversación (varios turnos) y cambiar el LLM variant en el switch.
2. Recargar la página (F5).

**Esperado**: el transcript (`messages`) y el `llmVariant` se rehidratan desde `localStorage` (clave `chat`). El estado transitorio (tool cards en curso, findings, status) NO se rehidrata (arranca limpio). `session_id` persiste vía cookie `agrosat-session-id`. Sin hydration mismatch (transcript bajo `<ClientOnly>`).

## Flujo 6 — Caída de red → retry+backoff
1. Enviar un mensaje. En DevTools → Network, throttle a **Offline** justo antes/durante el primer `read()` (corte pre-delta).
2. Volver a **Online** dentro de la ventana de reintentos.

**Esperado**:
- Cortes transitorios (red / 5xx / corte pre-delta) reintentan hasta 3 veces con backoff exponencial + jitter (500ms base, x2, cap 8000ms); en consola `[useChat] transient transport error (attempt n/4)`.
- Si la red vuelve, el turno se completa normalmente.
- Si se agotan los reintentos → `failTransport("network_error")`, status `error`.
- Corte POST-delta (texto ya streameado) NO reintenta (idempotencia) → `stream_interrupted`.
- 4xx/422 → fatal inmediato (`http_422`), sin reintentar.
- Abort (navegar fuera / `dispose`) → silencioso, sin error.

## Validación E2E en vivo (pendiente — `backend/.env.local`)

Los flujos 1–6 de arriba requieren la app levantada con backend real. En esta pasada (cierre
documental) NO se ejecutaron en navegador: el `backend/.env.local` está **AUSENTE** (falta
`DATABASE_URL` Postgres+PostGIS y las credenciales LLM Gemini/vLLM), y `/chat` necesita una sesión
sembrada en Postgres. Por eso la validación del frontend se hizo solo via vitest+typecheck+i18n+lint+build
(todos verdes). La demo en vivo queda como paso manual para cuando `.env.local` esté configurado.
Esto es una dependencia de **entorno** (secrets + DB), no un gap de calidad del código.

Pasos para la demo en vivo (cuando `.env.local` exista):
1. `cd backend && poetry run uvicorn backend.app.main:app --reload --port 8000` (con `.env.local` cargado).
2. Sembrar una sesión en Postgres (cookie `agrosat-session-id` + fila de sesión válida).
3. `cd frontend && pnpm dev`; abrir `http://localhost:3000` (`/`, `/es`, `/en`).
4. Ejecutar los flujos 1–6 (chat trilingüe, markdown, XSS, tool cards, reload-persiste, retry/backoff).
5. Opcional Playwright: `pnpm test:e2e` una vez exista `playwright.config.ts` y specs reales.
