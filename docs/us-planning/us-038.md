### Config Full-M (justificacion)

El default es "trimmed for L4" (`dim=128, depth 4+4, heads=4, dim_head=32`, docstring lineas 44-48). **Full-M**
sube la capacidad para acercarse al regimen del paper, manteniendo el modelo holgado en 96GB:

| Hiperparametro | L4 (actual) | **Full-M (propuesto)** | Justificacion |
|----------------|-------------|------------------------|---------------|
| `dim` | 128 | **192** | dimension de token; +50% capacidad sin disparar VRAM (el coste es lineal en dim para FF, cuadratico en atencion sobre tokens, no sobre dim). |
| `depth_temporal` | 4 | **6** | mas bloques sobre el eje temporal (la senal mas discriminativa segun TSViT); T completo justifica mas profundidad temporal. |
| `depth_spatial` | 4 | **6** | simetrico; 256 tokens espaciales toleran 6 bloques. |
| `heads` | 4 | **6** | mas cabezas de atencion (kwarg a exponer en factory). |
| `dim_head` | 32 | **64** | dim por cabeza estandar ViT (kwarg a exponer). `inner_dim = heads*dim_head = 384`. |
| `mlp_ratio` | 4 | **4** | se mantiene (expansion FF estandar). |
| `patch_size` | 8 | **8** | 16x16=256 tokens espaciales; bajar a 4 (1024 tokens) dispara la atencion espacial x16 -> reservar a "Full-L" futuro. |
| `n_timesteps` | 10 | **64** | T COMPLETO (>= T_max ~61); el dataset no recorta. |
| `batch_size` | 4 | **20** | aprovecha la H100 (Seccion 7). |
| `dropout` | 0.0 | **0.0-0.1** | opcional; 0.1 regulariza con la capacidad subida. Default 0.0 (paper) salvo overfit. |

> **Por que "Full-M" y no la config exacta del repo paper**: el repo `michaeltrs/DeepSatModels` usa
> `dim=128, depth=4-6, T por DOY real`. Nuestra "M" (medium) es un punto intermedio defendible que (a) cabe
> holgado en batch 20, (b) sube capacidad sobre el L4, (c) no exige reescribir la PE por DOY (que el pipeline
> actual no alimenta). Una "Full-L" (patch_size=4, dim=256, PE-DOY real) queda como trabajo futuro (ADR).

### Punto arquitectonico a verificar (no bloqueante, documentar)

El `to_seg` actual (`tsvit_wrapper.py:326`, `nn.Linear(dim, p*p)`) se aplica al tensor espacial **ya
reordenado a `(b k) n d`**, de modo que CADA clase tiene su propia rama espacial pero **comparten la misma
proyeccion lineal** `to_seg`. Esto es coherente con la separabilidad por cls-token de TSViT (la separacion vive
en los K cls-tokens del encoder temporal, no en la cabeza). **No se cambia**; se documenta como decision para
que el aumento de capacidad Full-M no induzca a "arreglar" algo que ya replica el paper.

### Presupuesto VRAM (Full-M 128px batch 20, AC-4)

- **Cota analitica**: el cuello de TSViT es la atencion. Temporal: `(B*N)` secuencias de `(K+T)` tokens dim
  `dim` -> con `B=20, N=256, K=18, T~61, dim=192`: la matriz de atencion temporal es
  `(B*N) x heads x (K+T) x (K+T)` = `5120 x 6 x 79 x 79` ~ 192M floats/capa (bf16 ~0.4 GB) x activaciones.
  Espacial: `(B*K)` secuencias de `N=256` tokens -> `360 x 6 x 256 x 256` ~ 142M floats/capa. **Estimacion
  total (modelo + activaciones + optimizer AdamW 2x params + AMP) ~ 25-40 GB** en batch 20 con T completo.
- **Veredicto**: **cabe holgado en 96GB** (criterio v8 lo confirma). Margen para subir batch si T real < 61.
  Si OOM (T muy largo + dim alto): bajar batch a 12-16 o `n_timesteps` a 45 (sigue siendo "casi-completo").
- **AMP bf16**: `use_amp=True` (autocast); la H100 tiene bf16 nativo -> ~2x throughput y mitad de memoria de
  activaciones vs fp32. El loop YA lo soporta (`torch.autocast`, `GradScaler`).

### Presupuesto de tiempo (40 epochs, AC-5)

- **Patches**: PASTIS folds 1,2,3 (train) ~ 1490 patches; fold 4 (val) ~ 490. Por epoch: ~75 steps train
  (batch 20) + ~25 val.
- **Cuello CPU**: el dataset NO colapsa tiempo (`collapse_time=None`), solo subsamplea/normaliza -> mas barato
  que el `np.median` 2D, pero leer T~61 frames por patch es I/O-bound. **Usar `--num-workers 8-12`**
  (persistent_workers + prefetch ya implementados) para no estrangular la H100.
- **Estimacion wall-clock**: con bf16 batch 20 en H100, ~**4-8 min/epoch** (transformer mas grande + T completo
  + I/O). **40 epochs ~ 3-5 h** (banda conservadora **3-6 h** incluyendo warmup de cache y el re-score fold-5).
  Cabe en una sola ventana H100. Auto-resume cubre cortes del tunel/sesion (AC-7).
- **`time-cap`**: no hay flag de cap horario en este CLI (lo tiene FarSLIP); el control es por `epochs=40` +
  auto-resume. Si la ventana se acaba, el run reanuda desde `last.pt`.
