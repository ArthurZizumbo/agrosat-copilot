## 2. Decisiones tecnicas (consultado Context7)

### D1 — Markdown: `marked` + `isomorphic-dompurify`

- **Lib**: `marked` (parser GFM, tablas + code blocks nativos, API sincrona `marked.parse(src)`).
- **Sanitizacion XSS (seguridad real)**: el output del LLM NO es confiable y puede traer HTML/`<script>`/`onerror`. `marked` **ya NO sanitiza** (la opcion `sanitize` esta deprecada/eliminada). Se sanitiza con **`isomorphic-dompurify`** (DOMPurify que funciona en server Node y cliente -> **SSR-safe**, evita `window is not defined` en SSR). Patron oficial Context7:
  ```ts
  // utils/markdown.ts
  import { marked } from "marked";
  import DOMPurify from "isomorphic-dompurify";
  marked.use({ gfm: true, breaks: true });
  export function renderMarkdown(src: string): string {
    return DOMPurify.sanitize(marked.parse(src, { async: false }) as string);
  }
  ```
  Se hace `marked.use({ hooks: { postprocess: DOMPurify.sanitize } })` o se sanitiza la salida; ambos validos. Elegimos sanitizar la salida explicitamente en la util (mas testeable). El `v-html` SOLO recibe HTML ya sanitizado. **Nunca** `v-html` sobre el raw del LLM.
- **Por que marked y no markdown-it**: marked tiene API sincrona mas simple, GFM por defecto, y el patron DOMPurify es el documentado oficialmente. markdown-it requiere mas plugins para tablas y su `html:true` es mas peligroso. DX en Nuxt: marked es un solo import, sin config de plugins.
- **Solo turnos assistant** se renderizan como markdown; el turno user sigue `whitespace-pre-wrap` (texto del propio usuario, no necesita markdown y reduce superficie XSS).

### D2 — Persist: `pinia-plugin-persistedstate/nuxt`

- **Integracion**: modulo Nuxt (no plugin manual). En `nuxt.config.ts` agregar `"pinia-plugin-persistedstate/nuxt"` a `modules` DESPUES de `@pinia/nuxt` (requerido). El modulo registra el plugin y expone `piniaPluginPersistedstate.localStorage()` global.
- **Que persiste** (`persist` en el options-store): `messages`, `llmVariant`. **NO** persistir estado transitorio de turno (`toolCalls`, `perceiverNotes`, `findings`, `status`, `activeAssistantId`, `errorMessage`, `toolSeq`) — son por-turno y reabrir con un tool "running" colgado seria incorrecto. Config con `pick`:
  ```ts
  persist: {
    storage: piniaPluginPersistedstate.localStorage(),
    pick: ["messages", "llmVariant"],
  }
  ```
- **`session_id`**: vive en `useSession()` (cookie `agrosat-session-id` + `useState`), YA persiste por cookie. No se duplica en el store. (El criterio "persist messages, session_id, llm_model" se satisface: messages+llmVariant via persistedstate, session_id via la cookie existente.)
- **SSR-safe**: `localStorage` solo existe en cliente. `piniaPluginPersistedstate.localStorage()` es no-op en server (el plugin guarda contra hidratacion). Como el store se hidrata en cliente, no hay mismatch SSR si el render del transcript es client-only o tolera vacio en server. **MessageBubble markdown render**: el HTML sanitizado es deterministico server/cliente (mismo input -> mismo output con isomorphic-dompurify), asi que no rompe hidratacion; el unico riesgo es que el server renderice transcript vacio y el cliente lo rehidrate desde localStorage -> usar `<ClientOnly>` alrededor de la lista de mensajes persistidos o aceptar el flash. **Decision**: envolver la lista de transcripto en `<ClientOnly>` en ChatDock para evitar hydration mismatch (messages vienen de localStorage, no del server).

### D3 — Retry + backoff exponencial

- **Donde**: en `useChat.sendMessage` (y/o un helper `streamWithRetry`). Reintenta el `fetch(apiUrl('/chat'))` + `readStream` completo cuando falla por error **transitorio**.
- **Estrategia**: `maxRetries = 3`, `baseDelayMs = 500`, backoff `base * 2**attempt` con **jitter** full (`delay * (0.5 + Math.random()*0.5)`), techo `maxDelayMs = 8000`.
- **Transitorio vs fatal**:
  - **Transitorio (reintenta)**: `TypeError`/network error del `fetch`; `res.status` 502/503/504 o >=500; corte del reader (`reader.read()` lanza) ANTES de recibir un evento terminal (`done`/`error`).
  - **Fatal (no reintenta)**: `AbortError` (stop/dispose intencional); `res.status` 4xx (incluido 422 = contrato malo, p.ej. `extra="forbid"`); evento `error` del backend (es respuesta valida del agente, no caida de transporte); stream que ya emitio `done`.
  - **Idempotencia**: si ya llegaron `text_delta` al store y el stream se corta, NO reintentar duplicaria texto. Politica: solo se reintenta si el corte ocurre **antes de cualquier `text_delta`** del turno actual (rastreado por un flag `receivedDelta`); si ya hubo deltas, se hace `failTransport("stream_interrupted")` sin retry. Esto evita texto duplicado/incoherente.
- **UX**: durante los reintentos `status` permanece `dispatching`/`streaming`; tras agotar reintentos -> `failTransport`. Opcional clave i18n `chat.reconnecting`.

### D4 — Locale en el payload (REQUIERE cambio en backend, ver R5)

- **Origen**: `const { locale } = useI18n()` -> `locale.value` (`"it"|"es"|"en"`). En `useChat.ts` (composable, SSR-safe; el envio solo corre en cliente con `import.meta.client`).
- **Body**: `body.locale = locale.value`.
- **Contrato backend**: `ChatRequest` en `backend/app/services/chat_service.py` tiene `model_config = ConfigDict(extra="forbid")` -> enviar `locale` hoy provoca **HTTP 422**. **Se requiere** agregar `locale: str | None = None` (o `Literal["it","es","en"]`) a `ChatRequest` y que el service lo inyecte como instruccion de idioma al reasoner. **Anotado como dependencia de backend (R5).** Mientras no se aplique, el front se codea pero `locale` se manda solo si una feature-flag/env lo habilita, o el cambio backend se hace en el mismo PR (preferido, es 2 lineas + 1 de prompt).

## 7. Riesgos

| ID | Riesgo | Mitigacion |
|----|--------|------------|
| R1 | **XSS** via markdown del LLM (HTML/script/onerror) | `isomorphic-dompurify` sobre TODA salida de `marked` antes de `v-html`; user-turn sin markdown; test XSS load-bearing obligatorio |
| R2 | **Hydration mismatch** SSR: `messages` vienen de localStorage (cliente) pero el server renderiza vacio | Envolver la lista de transcript en `<ClientOnly>`; `localStorage()` storage es no-op en server |
| R3 | **Contrato backend** `extra="forbid"` rechaza `locale` (HTTP 422) | **R5**: agregar `locale` a `ChatRequest` backend en el mismo PR; el front no envia `locale` hasta que el backend lo acepte |
| R4 | **Texto duplicado** al reintentar tras recibir deltas | Flag `receivedDelta`: no reintentar despues del primer `text_delta`; reintento solo cubre el fallo temprano |
| R5 | **Dependencia backend** (locale) | Cambio minimo: `ChatRequest.locale: Literal["it","es","en"] \| None = None` en `chat_service.py` + inyectar instruccion de idioma en `_agent_messages`/prompt del reasoner. Coordinar con dueno de backend; 1 commit `feat(E7)` separado o incluido en el PR |
| R6 | `marked` API: opcion `sanitize` eliminada en v12+ | NO usar `sanitize`; usar DOMPurify externo (patron oficial Context7) |
| R7 | `pnpm-lock.yaml` conflictos entre subtareas | Un solo `pnpm add` de las 3 deps antes de A/B/C |
| R8 | i18n parity rota (clave en 1 solo locale) | Agregar cada clave a it+es+en juntas; `pnpm i18n:check` en QA gate |
