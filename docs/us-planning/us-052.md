### 0.3 Hallazgos críticos verificados (leyendo el código)

1. **El hardcode de modelo NO está donde dice el AC original.** `chat_service.py` ya migró a `gemini-2.5-pro`
   (líneas 74 `_VARIANT_TO_MODEL["gemini"]`, 80 `_DEFAULT_MODEL`). El `gemini-3.1-pro` vive SOLO en
   `config.py:89` (`gemini_model`) y **el chat_service NUNCA lee `settings.gemini_model`** — resuelve el modelo
   vía `_VARIANT_TO_MODEL[llm_variant_default]`. Cambiar el modelo requiere tocar AMBOS sitios para coherencia.
2. **RIESGO DE SEGURIDAD: la RLS de US-051 NO aplica a las tools del /chat hoy.** El `ChatService._build_context`
   construye `ToolContext(pool=await ml.agent.db.get_pool())`, y `ml/agent/db.get_pool()` lee
   `settings.database_url` (rol superuser `agrosat` → **BYPASSRLS siempre, incluso con FORCE**). US-051 creó el
   rol `agrosat_app` (NOBYPASSRLS) y el pool `backend.app.core.db.get_pool()` que SÍ usa `app_database_url`.
   Las tools scopean vía `ml/agent/db.session_scoped_conn` (emiten `SET LOCAL app.current_session`), pero al
   correr como superuser ese `SET LOCAL` es decorativo: **no aísla**. Para cumplir el AC RLS hay que hacer que el
   `ToolContext` del /chat use el pool `app_database_url` (ver B2, Decisión D3).

## 2. Arquitectura del `/chat` endurecido

### 2.1 Diagrama de flujo

```
POST /chat (X-Session-ID, body)
   │
   ▼
[SlowAPIMiddleware / @limiter.limit("10/minute", key_func=session_id_key)]   ◄── B1
   │   └─ 11ª req/min misma sesión → 429 (RateLimitExceeded handler, antes de stremear)
   ▼
[Depends(verify_chat_session)]  ◄── B2 auth-guard
   │   ├─ parse_session_id(X-Session-ID)  → 400 si malformado/faltante
   │   └─ get_scoped_conn → SELECT 1 FROM chat_sessions  (RLS: solo ve la suya)
   │        └─ 0 filas → 403 (sesión inexistente o ajena)
   ▼
[chat router]  resuelve session_id, instancia ChatService(), devuelve StreamingResponse
   │
   ▼
[ChatService.stream()]
   │   ├─ _build_context(session_id) → ToolContext(pool = backend.app.core.db.get_pool())  ◄── B2 (app_database_url, NOBYPASSRLS)
   │   ├─ perceiver.observe() → emit  event: perceiver_observation
   │   └─ create_agent(model="gemini-3.5-flash").stream_response()   ◄── B1 modelo
   │         └─ loop: tool_call → [tool corre bajo session_scoped_conn → RLS aplica] → tool_result → text_delta → done
   ▼
text/event-stream  (event: text_delta / tool_result / done / error)
```

### 2.2 Dónde vive el rate-limit (decisión)

- **Decorador `@limiter.limit("10/minute")` sobre el endpoint**, NO `SlowAPIMiddleware` global.
  Razón: el middleware aplica `default_limits` a TODAS las rutas (incluye `/healthz`), y necesitamos
  `key_func` por sesión solo en `/chat`. El decorador permite `key_func` por endpoint.
- **Gotcha slowapi + StreamingResponse (verificado en Context7):** el decorador exige un parámetro
  `request: Request` en la firma del endpoint (slowapi lo inspecciona). El límite se evalúa **antes** de
  construir el `StreamingResponse` (en la fase de routing), por lo que NO interfiere con el cuerpo del stream:
  un `429` se devuelve como respuesta JSON normal antes de abrir el `text/event-stream`. Sin gotcha de buffering.
- `app.state.limiter = limiter` + `app.add_exception_handler(RateLimitExceeded, _rate_limit_exceeded_handler)`
  en `main.py::create_app`.

## 8. Decisiones a resolver (resueltas en este plan)

- **D1 (modelo, desviación AC):** AC original pedía `gemini-2.5-pro`; **Arthur decide `gemini-3.5-flash`**
  (más barato/rápido para el copiloto, suficiente con 1M ctx). Se documenta como **desviación consciente del AC**.
  No se usa el viejo hardcode `gemini-3.1-pro`.
- **D2 (fuente única del modelo):** `_reasoner_model()` del chat_service leerá `settings.gemini_model` para el
  variant `gemini` (en vez del literal en `_VARIANT_TO_MODEL`), dejando `config.py` como fuente única; `qwen35`
  sigue mapeado por dict. Se mantiene `_DEFAULT_MODEL` como fallback defensivo = `gemini-3.5-flash`.
- **D3 (RLS por request):** el `/chat` **NO scopea a nivel endpoint para las tools** — delega en las tools
  (`session_scoped_conn`), PERO requiere que el pool del `ToolContext` use `app_database_url` (NOBYPASSRLS).
  **B2 cambia `_build_context` a `backend.app.core.db.get_pool()`.** El `get_scoped_conn` del endpoint se usa
  SOLO para el **auth-guard** (`SELECT 1 FROM chat_sessions`), no para el stream.
- **D4 (modelo en ml/agent):** se actualizan también `agent.py::DEFAULT_MODEL` y `backends.py::_DEFAULT_GEMINI_MODEL`
  a `gemini-3.5-flash` por coherencia, ya que son los defaults cuando no se pasa modelo. Cambio cosmético (el
  chat_service siempre pasa el modelo explícito), pero evita drift documental.
- **D5 (auth-guard pragmático MVP):** sin Clerk productivo, el guard mínimo = `X-Session-ID` UUID válido (400) +
  existencia/pertenencia en `chat_sessions` vía RLS (403). No se valida `user_id` (demo). Suficiente para el MVP
  y cumple el AC "guard de autorización por sesión".
