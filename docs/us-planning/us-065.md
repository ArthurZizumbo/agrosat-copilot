# US-065 — Observabilidad de chat: structlog + MLflow tags + latencia p95

> EPIC 10 (Observabilidad y documentacion). Estimacion: 3 SP (~1.5 dias).
> Rama: `feature/E10-observabilidad-docs` (parte de `feature/E12-transfer-multiregion`).
> Plan de referencia: `context/RefinamientoPlaneacionAgroSatCopilot_v8.md` lineas 2106-2126.

## 1. Objetivo

Dotar a la capa conversacional (`/chat` SSE) de **observabilidad estructurada** y
**lineage reproducible**, de modo que se puedan verificar los SLOs de latencia del
chat (p95 < 3 s en query simple, < 15 s en multi-step) y que cada turno quede
trazable con su modelo activo, conteo de tool-calls y tokens consumidos (insumo
FinOps del switch A/B de US-054). El trabajo se apoya en lo ya emitido por
`ChatService` y por el `Agent` (eventos `agent_turn_*`), cerrando las brechas
reales: hoy **no se loggea latencia por turno end-to-end como metrica explicita de
SLO, ni conteo de tool-calls, ni tokens**, y el `DoneEvent` no transporta `usage`.

Esta US es de capa plataforma: no introduce modelos de ML nuevos. La regla de
Arthur aplica integra: **datos reales, nada sintetico ni placeholders**; todo lo
que no se pueda correr/verificar se anota en `docs/blockers/epic10-notas.md` y se
sigue.

## 2. Criterios de aceptacion (verbatim del plan v8)

- Metricas de chat en logs estructurados (`structlog.get_logger()`, nunca
  `print()`): latencia por turno con objetivos **p95 < 3 s simple** y **< 15 s
  multi-step**, conteo de tool-calls por mensaje, tokens y modelo activo (Gemini
  Pro/Flash/Qwen) para FinOps.
- Lineage de experimentos en MLflow (server **Docker :5010**, no `./mlruns`) con
  tags `data_version` + `code_version`; documentar el gotcha de los dos almacenes
  (runs por subprocess quedan RUNNING contra el server equivocado).
- Dependencia funcional de US-052 (`/chat` SSE) para tener trafico real que medir;
  mientras tanto, instrumentacion lista y validada con un flujo sintetico.
- Integracion con el scaffolding de Prometheus/Grafana de US-059 (el panel
  "latencia chat p95" se puebla aqui).

### Tareas tecnicas (verbatim del plan v8)

- [ ] Middleware/instrumentacion structlog de latencia y tokens por turno de chat
- [ ] Helper de logging de tool-calls y modelo activo (FinOps)

## 3. Estado actual verificado (linea base real)

Lo que YA existe y no se reescribe (verificado esta sesion):

- `backend/app/services/chat_service.py` ya emite con `structlog`:
  - `chat_stream_started` (`session_id`, `n_messages`, `has_parcel`, `has_aoi`).
  - `chat_model_resolved` (`session_id`, `variant`, `model`, `latency_ms` de la
    resolucion del reasoner: lectura DB + build del backend).
  - `chat_stream_finished` (`session_id`, `perceiver_observation_emitted`,
    `duration_ms` end-to-end via `time.perf_counter()`).
- `ml/agent/agent.py` ya emite `agent_turn_started` (con `model`, `n_tools`,
  `n_messages`), `agent_loop_completed` (con `turns`), `agent_turn_finished` (con
  `duration_ms`), y eventos por tool (`agent_unknown_tool`, `agent_tool_args_invalid`).
- `ml/agent/events.py`: union `AgentEvent` con `ToolCallEvent`, `ToolResultEvent`,
  `TextDeltaEvent`, `DoneEvent`, `ErrorEvent` (todos `frozen=True`,
  `extra="forbid"`). El `DoneEvent` hoy solo lleva `type`.
- `backend/app/core/config.py`: `Settings` con `extra="forbid"` ya declara
  `prometheus_pushgateway` y `sentry_dsn` (ambos vacios por defecto).

Brechas reales que esta US debe cerrar (no asumir que ya existen):

1. **No hay metrica de latencia por turno categorizada por SLO** (simple vs
   multi-step). `chat_stream_finished.duration_ms` existe pero no clasifica el
   turno ni evalua el umbral; falta una clave dedicada (p.ej. `chat_turn_metrics`).
2. **No se cuentan los tool-calls por mensaje**: el servicio reenvia eventos del
   agente pero no agrega un contador por turno.
3. **No se propagan tokens**: `BackendChunk` (`ml/agent/backends.py`) expone solo
   `text` + `function_call`; **no transporta `usage_metadata`** del proveedor. El
   `DoneEvent` no lleva `usage`. Sin tocar el contrato del backend no hay tokens
   reales que loggear -> es el riesgo R1 (ver seccion 6).
4. **No existe middleware** util: `backend/app/middleware/` solo tiene
   `__init__.py` vacio.
5. **No hay instrumentacion Prometheus**: `prometheus-client` NO esta instalado;
   no hay `/metrics`, ni `infrastructure/grafana/`. US-059 dejo el scaffolding como
   pendiente; esta US puebla el panel "latencia chat p95" pero la instalacion del
   exporter es prerequisito (coordinar con US-059, ver dependencia).

### 4.4 Dependencias del contrato de eventos (decision R1)

Para loggear **tokens reales** (no placeholders) hace falta propagar `usage` desde
el proveedor. Opcion preferida, minima y reversible:

- `ml/agent/backends.py`: anadir un campo opcional `usage` a `BackendChunk`
  (`UsageMetadata | None = None`, con `prompt_tokens` / `completion_tokens` /
  `total_tokens`), poblado SOLO cuando el SDK lo expone (`response.usage_metadata`
  en Gemini; `chunk.usage` en el stream OpenAI-compatible de vLLM/Qwen). Si el
  proveedor no lo entrega en streaming, queda `None`.
- `ml/agent/events.py`: anadir campo opcional `usage: dict | None = None` a
  `DoneEvent` (mantiene `frozen`/`extra="forbid"`; al ser opcional no rompe la
  union ni los tests existentes de round-trip).
- `ml/agent/agent.py`: acumular el `usage` del ultimo chunk del loop y adjuntarlo
  al `DoneEvent`.

Si tras inspeccionar los SDK reales el `usage` NO esta disponible en modo stream
(p.ej. Gemini solo lo da en respuesta no-stream), se documenta como limitacion:
los tokens se reportan `None`/`unknown` en `chat_turn_metrics`, se anota en
`docs/blockers/epic10-notas.md` y se sigue (NO se inventan tokens sinteticos). El
resto de la US (latencia + tool-calls + modelo activo) se entrega completo.

## 5. Enfoque tecnico

1. **Latencia por turno con SLO**: el helper clasifica el turno por numero de
   tool-calls observados en el stream (0 -> `simple`, >=1 -> `multi_step`),
   compara `duration_ms` end-to-end (ya medido por `ChatService.stream` con
   `time.perf_counter()`) contra `3000`/`15000` ms y emite `chat_turn_metrics`
   con `slo_met: bool`. Una sola fuente de verdad de la latencia: el timer del
   servicio, no uno nuevo.
2. **Tool-calls por mensaje**: el servicio ya itera los `AgentEvent`; basta
   incrementar el acumulador al reenviar cada `ToolCallEvent`. Cero coste extra.
3. **Modelo activo (FinOps)**: `variant` + `model` ya estan resueltos y loggeados
   en `chat_model_resolved`; se propagan al `chat_turn_metrics` para cruzar costo
   por modelo (Gemini Pro/Flash/Qwen) en el dashboard FinOps (insumo US-067).
4. **Tokens**: via el campo `usage` del `DoneEvent` (4.4). Reales o `None`, nunca
   sinteticos.
5. **Prometheus**: el helper expone un `Histogram` de latencia
   (`chat_turn_duration_seconds`, label `turn_type`) y `Counter` de tool-calls y
   tokens (labels `model`, `variant`), registrados de forma perezosa para no
   acoplar el arranque ni los tests al exporter. El panel Grafana consulta el p95
   con `histogram_quantile(0.95, ...)`.
6. **MLflow lineage**: verificar (no re-implementar) que los runs de entrenamiento
   relacionados llevan tags `data_version` + `code_version` contra el server
   Docker `:5010`. Documentar el gotcha de los dos almacenes (runs por subprocess
   quedan RUNNING contra el server equivocado) en `docs/observability/chat-metrics.md`
   con enlace a la nota de memoria existente. Esto es verificacion + doc, no codigo.
7. **Validacion con flujo sintetico** (mientras llega trafico real de US-052): los
   tests inyectan un agente stub que emite una secuencia conocida de eventos
   (`tool_call` x N -> `text_delta` -> `done` con `usage`) y se asserta el
   `chat_turn_metrics` resultante. Esto es flujo de prueba controlado, NO datos
   sinteticos de produccion: valida la instrumentacion, no falsea metricas.

## 6. Riesgos

- **R1 (alto) — tokens no disponibles en streaming**: si el SDK Gemini /
  OpenAI-compatible no expone `usage` en modo stream, no hay tokens reales. Plan:
  intentar propagar `usage` (4.4); si no se puede, reportar `None`, anotar en
  `docs/blockers/epic10-notas.md` y seguir. NUNCA inventar tokens.
- **R2 (medio) — dependencia de US-052 para trafico real**: `/chat` SSE debe
  existir para medir trafico real. Si no esta activo, la instrumentacion se valida
  con flujo sintetico (stub de agente) y se anota la pendiente de validacion con
  trafico real.
- **R3 (medio) — scaffolding US-059 ausente**: `prometheus-client` no instalado,
  sin `/metrics` ni `infrastructure/grafana/`. El export Prometheus se entrega como
  scaffolding gated (no-op si falta el exporter); el panel Grafana es plantilla. Si
  la instalacion de `prometheus-client` choca con pins congelados, blocker + modo
  solo-structlog.
- **R4 (bajo) — gotcha MLflow dos almacenes**: runs por subprocess quedan RUNNING
  contra el server equivocado. Mitigacion: doc explicita + verificacion de tags
  contra `:5010`, no `./mlruns`.
- **R5 (bajo) — extra="forbid"**: anadir flag Prometheus a `.env.local` sin
  declararlo en `config.py` rompe el arranque. Mitigacion: declarar primero en
  `Settings`.
- **R6 (bajo) — make check / lint frontend**: `pnpm lint` esta roto pre-existente
  (ESLint v9 sin `eslint.config.js`), ajeno a esta US backend/ml. Validar lint
  backend/ml por separado; gitleaks puede no estar instalado local.
