# US-056 — Worker de inferencia con cola Pub/Sub (scaffolding honesto) — planning

**Estado:** planning
**Epic:** E8 (Backend API + Worker Pub/Sub + Tiling)
**Avance:** A6 (despliegue + app MVP, 27-jun)
**Sprint:** S8
**Rama:** `feature/E8-US-056-pubsub-worker` (creada desde la rama de US-055).
**Carácter:** **DIFERIDA / FUTURE** — US-056 está marcada OUT del MVP en el plan v8 (§1 OUT, §9.2; [ADR-009](../decisions/ADR-009-h100-reactivacion-pivote-farslip-alcance-v8.md)). El MVP corre inferencia **síncrona**; esta US entrega solo el **scaffolding honesto** de la interfaz async + su documentación, NO un worker Pub/Sub productivo.
**Depende de:** US-051 (`get_settings`, RLS), US-052 (`/chat` SSE + perceiver/reasoner), el tool `classify_new_parcel` de `ml/agent/tools/classify.py` (la inferencia síncrona real que el modo `sync` reutiliza).

> Regla global NON-NEGOTIABLE: router fino → service → model; `structlog` (con `job_id` trazable); type hints completos; secrets solo vía `get_settings()`; sin emojis.
> **Regla de honestidad (Arthur):** CERO stubs que finjan éxito. El modo `sync` DEBE correr de verdad (invoca la inferencia ligera existente); el modo `pubsub` DEBE fallar claro (`NotImplementedError` explícito, no no-op silencioso). La doc deja claro que la cola async es FUTURE.

## 0. Estado real verificado (factual)

- **El MVP no requiere inferencia pesada.** El copiloto sirve clasificación de cultivo con el miembro `xgb-alphaearth` (tabular, CPU-light, `functools.lru_cache`) sobre parcelas PASTIS pre-cargadas + embeddings AlphaEarth ya materializados. Es lo que ya hace `ml/agent/tools/classify.py::run` (verificado: CPU-only, sin GPU, sin Pub/Sub).
- **`backend/app/core/config.py`** ya declara `pubsub_inference_topic = "inference-jobs"` (línea 64) y `gcs_artifacts_bucket`, `gcp_project_id` — la interfaz puede nombrarlos sin tocar `Settings` (cero riesgo `extra="forbid"`).
- **`ml/agent/context.py`** ya define `DeferHook` (un hook `(job_name, payload) -> handle` opcional en `ToolContext`) que un worker real consumiría; en el MVP es `None` (no hay executor diferido wireado) y los tools deferred degradan controladamente. El `JobsService` MVP NO usa ese hook (corre inline).
- **`ml/workers/` NO existía** — se crea como paquete nuevo.
- El plan v8 §9.3 ordena explícitamente: **"NO demostrar cola Pub/Sub real"** en la presentación.

## 2. Arquitectura

### 2.1 Decisión clave — dos modos de encolado, ninguno fingido

```
JobsService(enqueue_mode=...)
    sync  (MVP, default, REAL)   -> submit_job corre la inferencia INLINE
                                    (delega a classify_new_parcel) -> job DONE/FAILED
    pubsub (FUTURE, Full-only)  -> submit_job lanza NotImplementedError claro
                                    (apunta al topic inference-jobs + ADR-009/012)
```

- **`sync` es real:** `submit_job` construye un `ClassifyParcelInput` desde el `JobRequest`, arma un `ToolContext` session-scoped y ejecuta el runner (por default el tool `classify_new_parcel`). Devuelve el `job_id`; el job ya está `DONE` (o `FAILED` con error estructurado) cuando retorna. `get_job_status(job_id)` refleja el estado terminal de inmediato.
- **`pubsub` es FUTURE:** lanza `NotImplementedError` con mensaje *"Pub/Sub mode is Full-only (US-056 deferred, ADR-009)"*. Jamás no-op silencioso.
- **Modelos pesados en `sync`:** un `model_id` fuera de `{xgb-alphaearth, stacking-5}` devuelve `FAILED` con error honesto ("heavy models run on the Full Pub/Sub GPU worker"), no se sirve inline fingiendo.

### 2.2 El worker `ml/workers/inference_worker.py` — esqueleto documentado

- `handle_message(message)` — la FORMA del callback del subscriber Full: `validate -> infer (GPU) -> persist (GCS) -> publish (inference-results) -> ack`; en fallo transitorio `nack` (retry / DLQ). Un mensaje que no valida es poison message → `ack` (drop), no loop infinito.
- `parse_job_request(data)` — REAL (sin GCP): parsea + valida el body a `JobRequest`. Es la frontera que protege la inferencia de un mensaje malformado.
- `_run_inference` / `_publish_result` — `NotImplementedError` explícitos (GPU + GCS + publish son Full-only). Nunca fabrican resultado.
- `run_subscriber()` y `if __name__ == "__main__"` — **no arrancan un subscriber real**: lanzan `NotImplementedError` explicando que requieren GCP Pub/Sub + Cloud Run GPU L4. El flujo completo (Pub/Sub → callback → GCS → inference-results → SSE → frontend) está en el docstring del módulo.

### 2.3 Modelos Pydantic (validación antes del service)

- `JobRequest{session_id: UUID, aoi_geojson: GeoJSONGeometry, model_id: str, year: int, params: dict}` — `extra="forbid"`. La AOI se valida con `GeoJSONGeometry` (tipos OGC permitidos + coords no vacías) ANTES de que el service corra.
- `JobStatus{job_id, state: JobState, result_url, result: ClassificationResult | None, error}`.
- `JobState` (`StrEnum`): `queued / running / done / failed`. El MVP `sync` solo emite `done` / `failed`; `queued` / `running` son para el worker Full.
- `InferenceResult{job_id, session_id, state, result_url, error}` — schema del topic `inference-results`.

### 2.4 Cero variables nuevas en `Settings`

Se reusan `pubsub_inference_topic`, `gcp_project_id`, `gcs_artifacts_bucket` (ya declaradas). Sin riesgo `extra="forbid"`.

## 4. Plan de tests (solo lo real, sin Pub/Sub mockeado)

1. `test_sync_mode_runs_inline_and_returns_done` — `submit_job` corre el runner inline → `DONE` + `job_id` (uuid4 hex de 32) + result inline. **AC del modo sync.**
2. `test_sync_mode_passes_request_through_to_runner` — los campos del `JobRequest` (session_id, aoi, use_stacking, label_space) llegan al `ClassifyParcelInput`; el `ToolContext` es session-scoped. **Multi-tenant.**
3. `test_get_job_status_unknown_id_is_none` — id desconocido → `None` (sin crash).
4. `test_sync_mode_inference_failure_is_failed_state` — el runner lanza → `FAILED` con el mensaje de error.
5. `test_sync_mode_heavy_model_degrades_to_failed_not_faked` — `model_id` GPU → `FAILED` honesto; el runner NUNCA se invoca (no se finge).
6. `test_pubsub_mode_raises_clear_not_implemented` — modo `pubsub` → `NotImplementedError` con "Pub/Sub mode is Full-only" + "US-056" + "ADR-009" + "inference-jobs".
7. `test_default_enqueue_mode_is_sync` — el default del MVP es `sync` (ADR-012).
8. `test_job_request_accepts_valid_payload` — payload válido valida con defaults (`xgb-alphaearth`, 2019).
9. `test_job_request_rejects_invalid_geometry_type` — tipo GeoJSON no soportado → `ValidationError`.
10. `test_job_request_rejects_empty_coordinates` — coords vacías → `ValidationError`.
11. `test_job_request_rejects_extra_keys` — `extra="forbid"` → `ValidationError`.
12. `test_job_status_terminal_carries_no_partial_result` — `FAILED` lleva error y NO result (degradación honesta).

**NO se testea** un Pub/Sub real ni mockeado (no hay subscriber corriendo).

## 5. Riesgos

| # | Riesgo | Mitigación |
|---|--------|-----------|
| R1 | Que el scaffolding "finja" estar terminado | Modo `sync` es real (invoca el tool); modo `pubsub` + worker loop fallan con `NotImplementedError` explícito; doc dice FUTURE en todos lados. |
| R2 | Registro de jobs in-memory (`dict`) no sirve para inter-proceso | Válido en MVP (el `sync` completa antes de retornar); el Full lo persistirá en PostgreSQL. Documentado en el docstring + ADR-012 (consecuencias). |
| R3 | `google-cloud-pubsub` no instalado | El worker importa el tipo `Message` solo bajo `TYPE_CHECKING` (cero dependencia de runtime); `parse_job_request` no toca GCP. El módulo importa limpio. |
| R4 | Cargar el tool de clasificación arrastra ML pesado al importar el service | El runner default importa `classify` de forma lazy (dentro de `_default_runner`), así `jobs_service` importa sin polars/xgboost. |
| R5 | `extra="forbid"` en Settings | Cero variables nuevas (se reusan las existentes). |

## 6. Mapeo rúbrica A6

- **Ingeniería madura / honestidad:** la regla "inferencia >2 s vía Pub/Sub" se respeta en Full; el MVP sirve inferencia ligera síncrona de verdad y deja la interfaz async fijada, testeada (modo sync) y documentada (ADR-012), sin fingir una cola que no escala.
- **Trazabilidad:** `job_id` estructurado en todos los logs (service + worker), schema de mensajes validado por Pydantic.
- **Degradación honesta:** modo `pubsub` y modelos pesados fallan claro; un fallo de inferencia es `FAILED` con causa, nunca un éxito fabricado.
