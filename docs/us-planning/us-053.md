## 2. Arquitectura

### 2.1 Backend — 4 endpoints (router fino → service → DB RLS-scoped)

Todos los routers son **finos** (SoC, patrón US-052): resuelven `Depends(get_scoped_conn)` + `Depends(verify_session)` y delegan al service. Cero SQL en routers.

```
POST   /aois                     -> AoiService.create(conn, feature)      -> 201 AoiFeature
GET    /aois                     -> AoiService.list(conn)                 -> 200 AoiFeatureCollection
GET    /aois/{aoi_id}            -> AoiService.get(conn, aoi_id)          -> 200 AoiFeature | 404
DELETE /aois/{aoi_id}            -> AoiService.delete(conn, aoi_id)       -> 204 | 404
GET    /aois/{aoi_id}/timeseries -> TimeseriesService.for_aoi(conn, ...)  -> 200 TimeSeriesResponse | 404
GET    /tiles/{z}/{x}/{y}.png    -> (US-055 monta TilerFactory)           -> 501 (este US) | tile PNG (US-055)
GET    /stac/search              -> StacService.search(conn, q)           -> 200 ItemCollection (vacío si pgstac ausente)
```

**Decisión de capa de datos (resuelve la tensión plan v8 "SQLModel+GeoAlchemy2" vs código real asyncpg):**
**asyncpg directo via `get_scoped_conn`**, NO SQLModel/GeoAlchemy2 ORM. Razones:
1. **Coherencia con el código real**: `chat_service.py` y las 9 tools del agente (`classify`, `timeseries`, `aoi_stats`, `list_parcels`, ...) ya usan asyncpg directo. `backend/app/models/` está **vacío** (solo `__init__.py`). Introducir SQLModel async + GeoAlchemy2 aquí crearía **dos** capas de datos divergentes.
2. **RLS**: el contrato de aislamiento vive en `get_scoped_conn` (asyncpg). Montar una `AsyncSession` de SQLAlchemy encima requeriría re-emitir `SET LOCAL` por sesión SQLAlchemy y duplicar el contrato byte-a-byte; riesgo de fuga si se desincroniza.
3. **GeoJSON I/O nativo en Postgres**: `ST_AsGeoJSON(geom)` y `ST_SetSRID(ST_GeomFromGeoJSON($1),4326)` resuelven la conversión geometry↔GeoJSON en SQL, sin mapear `WKBElement` de GeoAlchemy2 en Python.
4. `backend/app/models/` se usa para **Pydantic response models** (no ORM): `AoiFeature`, `AoiFeatureCollection`, `TimeSeriesResponse`, `StacSearchQuery`, `StacItemCollection`. Esto respeta "router devuelve Pydantic, jamás SQLModel crudo".

> **Desviación documentada del plan v8** ("Modelos SQLModel+GeoAlchemy2"): se sustituye por asyncpg + PostGIS I/O + Pydantic response models, por coherencia con el backend existente y para no fracturar el contrato RLS. (Mismo criterio que US-051/052 ya aplicaron de facto.)

**GeoJSON contract (AC-6):**
- AOI de salida = GeoJSON `Feature`: `{type:"Feature", id, geometry:<Polygon>, properties:{label, area_ha, session_id_present:bool, created_at}}`. Lista = `FeatureCollection`.
- Entrada `POST /aois` = `Feature` (o geometría `Polygon` + `label`). Geometría validada con el `GeoJSONGeometry` ya existente en `ml/agent/schemas.py` (REUSAR — DRY) o un `AoiCreate` Pydantic local con el mismo validador OGC.
- INSERT: `INSERT INTO aois(session_id, geom, label, area_ha) VALUES (current_setting('app.current_session')::uuid, ST_SetSRID(ST_GeomFromGeoJSON($1),4326), $2, ST_Area(geom::geography)/10000) RETURNING id, ST_AsGeoJSON(geom), label, area_ha, created_at`. `session_id` NO viene del cliente: se toma del RLS hook (defensa: WITH CHECK de la política rechaza otro `session_id`).

**`/tiles` (AC-3) — contrato:**
- US-055 montará `TilerFactory(...).router` con `prefix="/tiles"` (TiTiler sirve COG/AlphaEarth). Para US-053 el `TilerFactory` **aún no se monta** (evita acoplar la imagen ahora).
- US-053 registra `tiles.router` con un handler **stub documentado** que devuelve `501 Not Implemented` + body `{"detail":"Tile serving is mounted by US-055 (TiTiler TilerFactory); not yet available.","contract":"GET /tiles/{z}/{x}/{y}.png"}`. Un comentario en `main.py` marca el punto exacto de montaje futuro del `TilerFactory`. **No proxy HTTP externo** (no hay tiler upstream que proxiar todavía); el `501` es la degradación honesta.

**`/stac/search` (AC-4) — contrato:**
- Query Pydantic `StacSearchQuery`: `bbox: BBox | None`, `datetime: str | None` (intervalo RFC 3339 STAC), `collections: list[str] | None`, `limit: int = 10`.
- `StacService.search`: detecta si `pgstac` existe (`SELECT 1 FROM pg_extension WHERE extname='pgstac'` — cacheado por proceso). **Ausente** → devuelve un `ItemCollection` **vacío válido** (`pystac.ItemCollection(items=[], extra_fields={"numberMatched":0,"numberReturned":0})` → `.to_dict()` = FeatureCollection GeoJSON con `features:[]`). **Presente** → `SELECT * FROM pgstac.search(:query::jsonb)` (CQL2/STAC API) y serializa las features como STAC Items. El contrato de salida es **idéntico** en ambos casos (FeatureCollection STAC), así el frontend no se rompe.
- Reutiliza el contrato `SearchStacInput`/`SceneList` de `ml/agent/schemas.py` donde aplique (la tool `search_stac` del agente y el endpoint deben hablar el mismo vocabulario).

### 2.2 ML — clasificador con 2 banderas + label-space registry (hook EPIC 12)

**(1) Label-space registry — `ml/eval/class_remap.py`** (se AMPLÍA el módulo existente; hoy solo tiene helpers de remap 20→18). Estructura: `@dataclass(frozen=True) LabelSpace` + un dict-registro module-level + `register_label_space()` / `get_label_space()`.

**Docstring del registry documenta el hook EPIC 12** (US-074 crosswalk HCAT): "Esta estructura permite añadir label-spaces futuros (`iberia-14`, `hcat-global-20`) registrándolos sin reescribir el clasificador. EPIC 12 US-074 ampliará el registro vía crosswalk HCAT (Harmonized Crop and Agricultural Types), mapeando los espacios nacionales a una taxonomía global."

**(2) Bandera `restrict_to_resolved_classes` (default ON)** — `ml/agent/tools/classify.py`. Enmascara las 9 clases mal resueltas del posterior `(18,)` de `xgb-alphaearth` y **renormaliza** sobre las 9 del label-space activo (`france-9`). CPU, cualquier parcela, desde la DB (solo necesita `alphaearth_embedding` 64-dim). Implementación: nueva función `_restrict_posterior(proba_18, label_space) -> dict[name, float]` que toma `proba_18[ids]`, renormaliza, y construye el dict con `label_space.class_names`. Cuando OFF → 18 clases como hoy.

**(3) Bandera `use_stacking` (default OFF)** — `ml/agent/tools/classify.py`. Para parcelas **ya materializadas del fold-5**: carga los 5 OOF parquets (`ml/eval/oof/oof_parcel_<member>_fold5.parquet`), re-fitea el meta-learner logreg (NO persistido) vía `StackingEnsemble(base_members=(...5...), meta="logreg")` y devuelve el posterior del Stacking-5 campeón (F1-macro 0.912 con 9 clases). Para un polígono **NUEVO sin OOF** (no está en fold-5) → degrada limpio a `xgb-alphaearth` + bandera (1). **Si los OOF no están (DVC no pulled / FileNotFoundError)** → degrada a xgb con `logger.warning("classify_stacking_unavailable", reason=...)`, **NO crashea** (AC-8). Implementación: helper `_stacking_posterior_for_parcel(canonical_parcel_id) -> np.ndarray | None`; resolución parcela→`canonical_parcel_id` vía la parcela persistida que intersecta el AOI (reusa `_fetch_parcel_embedding` para obtener el id de parcela; el `canonical_parcel_id` se deriva de `parcels` + el bridge de `ml.utils.parcel_id`). Si no hay match en el universo fold-5 → `None` → degrada.

**(4) Schema** — `ml/agent/schemas.py::ClassifyParcelInput` gana **2 campos** opcionales con defaults:
```python
restrict_to_resolved_classes: bool = True
use_stacking: bool = False
```
Y se corrige el docstring de la clase ("StackingEnsemble inference" → la verdad). `ClassificationResult` NO cambia estructura (`crop_class`, `confidence`, `class_probabilities`) — solo el contenido (9 vs 18 entradas según bandera).

**(5) Descripción de la tool (AC-10)** — corregir el docstring del módulo `classify.py` y, si existe el `FunctionDeclaration`/registro de tools (`ml/agent/tools/__init__.py` o `function_declarations`), su `description`: "Classifies a parcel's crop. By default serves the **xgb-alphaearth tabular member** restricted to the active label-space's well-resolved classes; with `use_stacking=True` and cached fold-5 OOF available, serves the **Stacking-5** champion posterior. NOT a generic 'stacking ensemble' by default."
