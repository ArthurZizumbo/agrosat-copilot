# US-054 — POST /llm/switch A/B (4 variantes hibrido)

**Epic:** E8 · **Sprint:** S8 · **Avance:** A6 (MVP 27-jun) · **Rubrica:** A6 (trade-off costo/latencia + soberania de datos).
**Rama:** `feature/E8-US-054-llm-switch` (desde US-053).
**Cadena:** US-051 (RLS `get_scoped_conn`/`get_pool`), US-052 (`verify_chat_session` + `Limiter` por sesion + `ChatService._reasoner_model`), US-053 (patron router->service->`get_scoped_conn`).

## 1. Historia y criterios verificables

Como presentador de la demo quiero cambiar **en caliente** el modelo del orquestador para mostrar el trade-off
costo/latencia (Pro vs Flash) y la soberania de datos (cloud vs on-prem) **sin reiniciar la sesion**.

| AC | Criterio | Verificable por |
|----|----------|-----------------|
| AC-1 | `POST /llm/switch` persiste `chat_sessions.llm_model` (session-scoped, RLS US-051) y responde `200` con el modelo aplicado. | test integracion: switch -> SELECT scopeado retorna el valor. |
| AC-2 | Los `/chat` subsecuentes **de esa sesion** usan el nuevo modelo (HOY el `ChatService` lee `settings.llm_variant_default` GLOBAL -- ese es el cambio clave). | test: switch a `qwen-onprem` -> `/chat` instancia `VLLMOpenAIBackend` (mock por modelo). |
| AC-3 | 4 variantes soportadas: `gemini`, `qwen-api`, `qwen-onprem`, `gemma`. | CHECK constraint + routing table resuelve las 4. |
| AC-4 | Routing **agnostico de backend**: variante -> `(backend_type, base_url_env, api_key_env, model_id)`; cambiar H100/L4/API hosteada = cambiar env var, CERO codigo. | test parametrizado: cada variante resuelve su `(backend, base_url, model)` desde env vars. |
| AC-5 | Latencia y tokens loggeados por switch y por request (insumo FinOps US-065). | `logger.info("llm_switch", ...)` + `logger.info("chat_model_resolved", model=, latency_ms=, ...)`. |
| AC-6 | Guard de autorizacion por sesion (`verify_chat_session`) + rate limit **5/min** key=`session_id`. Nunca sin auth. | test: sin/foreign `X-Session-ID` -> 400/403; 6ta llamada en la ventana -> 429. |
| AC-7 | Demo verificable: misma query Pro->Flash ~3.5s vs ~1.2s; switch a `qwen-onprem` REAL (:8002) responde. | manual-test + validacion en vivo contra Qwen `:8002`. |
| AC-8 | Migracion `dbmate up`/`down` reversible sin romper filas existentes (DEFAULT `gemini`, dato `qwen35` migrado). | test round-trip up->down->up. |

## 2. Decisiones resueltas

### D1 — Schema: renombrar `llm_variant` -> `llm_model`, ampliar CHECK a 4 valores

Se **renombra** la columna (no se anade una segunda) para que el nombre exprese el dominio nuevo y no queden dos
columnas semanticamente solapadas. Valores **exactos persistidos** (string plano, 1:1 con una entrada de routing):

| Valor persistido | Backend | Soberania | Default |
|------------------|---------|-----------|---------|
| `gemini` | cloud (Vertex/AI Studio, google-genai) | cloud | **SI** (preserva el DEFAULT actual) |
| `qwen-api` | API OpenAI-compat hosteada (Together/Fireworks/OpenRouter) | cloud serverless | |
| `qwen-onprem` | Qwen vLLM self-hosted H100/L4 `:8002` | **on-prem** | |
| `gemma` | Google AI Studio o Ollama on-prem `:11434` | cloud u on-prem | |

String plano (no `{provider, model}` JSON): el CHECK valida exacto, mapea 1:1 a la routing table, y el `ChatService`
no parsea estructura. El **model id concreto** (`gemini-3.5-flash`, served-model `qwen35`, `gemma4:...`) NO se persiste
en la fila -- vive en env var / settings (D2), para que cambiar de modelo no toque datos.

**Migracion de datos** (rollforward, sin perder filas): las filas con `gemini` se mantienen; las `qwen35` -> `qwen-onprem`
(el `qwen35` historico ERA on-prem vLLM). DEFAULT sigue `gemini`. Receta (Postgres, drop+add CHECK por nombre):

```sql
-- migrate:up
ALTER TABLE chat_sessions DROP CONSTRAINT IF EXISTS chat_sessions_llm_variant_check;
ALTER TABLE chat_sessions RENAME COLUMN llm_variant TO llm_model;
ALTER TABLE chat_sessions ALTER COLUMN llm_model DROP DEFAULT;        -- soltar el default viejo antes de migrar dato
UPDATE chat_sessions SET llm_model = 'qwen-onprem' WHERE llm_model = 'qwen35';
ALTER TABLE chat_sessions
  ADD CONSTRAINT chat_sessions_llm_model_check
  CHECK (llm_model IN ('gemini', 'qwen-api', 'qwen-onprem', 'gemma'));
ALTER TABLE chat_sessions ALTER COLUMN llm_model SET DEFAULT 'gemini';

-- migrate:down  (reverso exacto: re-mapea qwen-onprem->qwen35, re-renombra, restaura CHECK de 2 valores)
ALTER TABLE chat_sessions DROP CONSTRAINT IF EXISTS chat_sessions_llm_model_check;
ALTER TABLE chat_sessions ALTER COLUMN llm_model DROP DEFAULT;
-- las variantes nuevas (qwen-api, gemma) caen a 'gemini' para no violar el CHECK viejo (down honesto, documentado)
UPDATE chat_sessions SET llm_model = 'qwen35' WHERE llm_model = 'qwen-onprem';
UPDATE chat_sessions SET llm_model = 'gemini' WHERE llm_model IN ('qwen-api', 'gemma');
ALTER TABLE chat_sessions RENAME COLUMN llm_model TO llm_variant;
ALTER TABLE chat_sessions
  ADD CONSTRAINT chat_sessions_llm_variant_check
  CHECK (llm_variant IN ('gemini', 'qwen35'));
ALTER TABLE chat_sessions ALTER COLUMN llm_variant SET DEFAULT 'gemini';
```

> Nota RLS: el `ALTER TABLE` corre como rol de migracion `agrosat` (superuser, BYPASSRLS) -> no choca con la policy
> `tenant_isolation`. El `UPDATE` del runtime (LLMSwitchService) SI corre scopeado por `agrosat_app` (D4).
> El nombre real del constraint inicial (`chat_sessions_llm_variant_check`) lo genera Postgres por convencion
> `<tabla>_<col>_check`; la migracion usa `DROP CONSTRAINT IF EXISTS` por ese nombre (verificar en `db-shell` con `\d chat_sessions` antes de aplicar).

### D2 — Routing table agnostica de backend

Tabla declarativa variante -> `(backend_type, base_url_env, api_key_env, model_id)`. Vive en un modulo nuevo
`ml/agent/llm_routing.py` (DRY: lo consumen `ChatService` y `make_backend`). `backend_type ∈ {gemini, openai_compat}`.

| Variante | backend_type | base_url (env) | api_key (env) | model_id (settings/env) |
|----------|--------------|----------------|---------------|--------------------------|
| `gemini` | `gemini` | n/a (SDK) | `GEMINI_API_KEY` / Vertex ADC | `settings.gemini_model` (`gemini-3.5-flash`) |
| `qwen-api` | `openai_compat` | `QWEN_API_URL` | `QWEN_API_KEY` | `QWEN_API_MODEL` (p.ej `Qwen/Qwen3-...`) |
| `qwen-onprem` | `openai_compat` | `VLLM_QWEN35_URL` (ya existe, `:8002`) | `VLLM_API_KEY` | served-model `qwen35` |
| `gemma` | `openai_compat` | `GEMMA_API_URL` o `OLLAMA_BASE_URL` | `GEMMA_API_KEY` (vacio para Ollama) | `GEMMA_MODEL` (`gemma4:...`) |

Cualquier endpoint OpenAI-compat sirve (Together/Fireworks/OpenRouter/vLLM/Ollama). Pasar de H100 a L4 a API = cambiar
`QWEN_API_URL`/`VLLM_QWEN35_URL`, **cero codigo** (AC-4). El `make_backend` actual ya selecciona `GeminiBackend` vs
`VLLMOpenAIBackend`/`OllamaBackend`; la tabla lo hace explicito y por VARIANTE (no por heuristica de prefijo del nombre).

### D3 — ChatService lee `llm_model` de la FILA de la sesion (cambio clave)

HOY `ChatService._reasoner_model()` lee `settings.llm_variant_default` (GLOBAL). El `/chat` ya recibe `session_id`.
Cambio: el `ChatService` consulta `SELECT llm_model FROM chat_sessions WHERE id = $1` **scopeado** (reusa el pool
`agrosat_app` que ya inyecta via `pool_factory`/`ToolContext`), resuelve via routing table (D2) y construye el backend.

- Lectura por sesion en `stream()` (antes de instanciar el agente), no en `__init__` (el service es por-request pero
  el modelo depende del `session_id` del request). Si la fila no trae valor o la variante es desconocida -> fallback
  `settings.llm_variant_default` -> `gemini` (degradacion honesta, `logger.warning`).
- `settings.llm_variant_default` se mantiene como **default de arranque/fallback** (no se borra), pero deja de ser la
  fuente por-request. El `_VARIANT_TO_MODEL`/`_reasoner_model` se reescriben para tomar la variante de la fila.

### D4 — `/llm/switch`: router fino -> `LLMSwitchService` -> UPDATE scopeado

- `POST /llm/switch`, body `{model: <una de las 4 variantes>}` (`LLMSwitchRequest`, `extra=forbid`, `model: Literal[...]`).
- Guard: `Depends(verify_chat_session)` (US-052, fail-closed 400/403) + `@limiter.limit("5/minute", key_func=session_id_key)`
  (US-052 `Limiter`, `settings.rate_limit_llm_switch_per_min` ya existe = 5).
- `LLMSwitchService.switch(conn, model)`: `UPDATE chat_sessions SET llm_model = $1, updated_at = now()` (RLS filtra a la
  propia sesion; `current_setting('app.current_session')` ya primado por `get_scoped_conn`). Responde `LLMSwitchResponse{model, applied_at}`.
- Logging: `logger.info("llm_switch", session_id=, model=, latency_ms=)` (AC-5).

## 3. Arquitectura

### Flujo switch
```
POST /llm/switch {model:"qwen-onprem"}  + X-Session-ID
  -> verify_chat_session (400 sin header / 403 foreign)  -> limiter 5/min (429 al 6to)
  -> get_scoped_conn (SET LOCAL app.current_session)
  -> LLMSwitchService.switch -> UPDATE chat_sessions SET llm_model='qwen-onprem' (RLS scopeado)
  -> 200 {model:"qwen-onprem", applied_at}
```

### Flujo /chat lee-por-sesion (cambio clave AC-2)
```
POST /chat  + X-Session-ID
  -> ChatService.stream(session_id)
       -> SELECT llm_model FROM chat_sessions WHERE id=session_id  (scopeado)
       -> resolve_routing(llm_model) -> (backend_type, base_url, api_key, model_id)
       -> make_backend(...) -> GeminiBackend | VLLMOpenAIBackend | OllamaBackend
       -> stream SSE (perceiver + reasoner con el backend nuevo)
```

### Routing table (4 variantes) -> backend
```
gemini       -> GeminiBackend(model=gemini_model)                         [cloud]
qwen-api     -> VLLMOpenAIBackend(QWEN_API_URL, QWEN_API_MODEL, QWEN_API_KEY)  [cloud serverless]
qwen-onprem  -> VLLMOpenAIBackend(VLLM_QWEN35_URL, "qwen35", VLLM_API_KEY)     [on-prem, :8002]
gemma        -> OllamaBackend(GEMMA_API_URL|OLLAMA_BASE_URL, GEMMA_MODEL)      [cloud u on-prem]
```

## 7. Riesgos

| Riesgo | Mitigacion |
|--------|------------|
| Cambiar CHECK constraint con datos existentes | drop+rename+UPDATE+add CHECK en una migracion atomica; round-trip test (T4); verificar nombre real del constraint en `db-shell` (A2). |
| Env vars faltantes (`QWEN_API_URL`, `GEMMA_API_URL`) degradan silenciosamente | `resolve_route` con fallback documentado + `logger.warning("llm_route_env_missing", variant=)`; manual-test lista las env requeridas por variante. |
| Qwen API key (`QWEN_API_KEY`) ausente | variante `qwen-api` es opcional para la demo; default `gemini`; `qwen-onprem` (`:8002`) NO requiere key real (`EMPTY`). Verificar key leyendo `.env.local` + probando la API, nunca por grep del shell (memoria env-local-keys). |
| `extra=forbid` rompe arranque si env var declarada en `.env.local` sin declarar en `Settings` | declarar las 6 env vars nuevas en `Settings` (B2) ANTES de anadirlas a `.env.local`. |
| `make_backend` por-prefijo se usa en el eval con model ids (`qwen36-vl`, `gemma4:...`) | NO cambiar la firma por-model-name de `make_backend`; la entrada por-variante es `make_backend_for_variant` (B6). |
| Lectura por sesion anade un SELECT por `/chat` | SELECT trivial sobre PK; reusa la conexion scopeada/pool ya abierta; despreciable. |

## 8. Mapeo rubrica A6

- **Trade-off costo/latencia**: switch `gemini` (Flash ~1.2s, barato) vs un Pro/`qwen-*`; latencia loggeada por switch y por
  `/chat` request (AC-5) -> evidencia FinOps US-065. Demo: misma query, dos modelos, dos latencias (AC-7).
- **Soberania de datos**: `qwen-onprem` (`:8002`, datos no salen del H100/L4) vs `gemini`/`qwen-api` cloud. El switch en
  caliente sin reiniciar sesion demuestra el control de soberania (AC-1/AC-2).
- **Diseno agnostico**: routing table env-driven (AC-4) = portabilidad H100/L4/API hosteada sin tocar codigo.
