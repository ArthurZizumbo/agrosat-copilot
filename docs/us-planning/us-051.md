### 0.2 Rol de la DB en docker-compose

- `docker-compose.yml`: `POSTGRES_USER=agrosat` → **es SUPERUSER** del cluster.
- **Punto crítico verificado en Context7** (`postgres/rls.c::has_bypassrls_privilege`): *"Superusers bypass all
  permission checking… always considered to have BYPASSRLS"*. Y `check_enable_rls`: el **owner de la tabla**
  bypassa RLS salvo `FORCE ROW LEVEL SECURITY`; pero el **superuser bypassa SIEMPRE, incluso con FORCE**.
- Implicación: si la app se conecta como `agrosat` (superuser), **la RLS no se aplica jamás** y el test de
  aislamiento sería un falso verde. → Hay que crear un **rol de aplicación no-superuser sin BYPASSRLS**, y el
  test de aislamiento debe correr como ese rol.

## 2. Grafo de ownership real → policy por tabla

Decisión de diseño por tabla. **`current_setting('app.current_session', true)` con `missing_ok=true`** para no
romper queries del propio agente cuando la sesión no está seteada (devuelve `NULL`; el cast `::uuid` de `NULL`
es `NULL`, y `col = NULL` es `NULL` → 0 filas, *fail-closed*).

| Tabla | Owner | Policy `tenant_isolation` (USING) | WITH CHECK (INSERT/UPDATE) | Notas |
|-------|-------|-----------------------------------|----------------------------|-------|
| `chat_sessions` | `id` (la sesión misma) | `id = current_setting('app.current_session', true)::uuid` | igual | La sesión solo se ve a sí misma. |
| `aois` | `session_id` (NOT NULL) | `session_id = current_setting('app.current_session', true)::uuid` | igual | Owner directo. |
| `parcels` | `session_id` (nullable) | `session_id = current_setting('app.current_session', true)::uuid` | igual | **Nullable**: filas con `session_id IS NULL` quedan ocultas a todos (también fail-closed). Aceptable para MVP (las parcelas demo se siembran con sesión). Documentar. |
| `features_parcels` | **indirecto** vía `parcel_id` | `EXISTS (SELECT 1 FROM parcels p WHERE p.id = features_parcels.parcel_id AND p.session_id = current_setting('app.current_session', true)::uuid)` | igual (subquery) | **No tiene `session_id`**; se aísla por subquery contra `parcels`. La policy de `parcels` también aplica dentro de la subquery (defensa en profundidad). |
| `rag_documents` | **ninguno** (corpus global) | **NO se habilita RLS** | — | Es corpus PASTIS-R compartido, no per-session. Se documenta explícitamente como out-of-scope de RLS (lectura pública para todos los tenants). |

**Tablas con RLS:** `chat_sessions`, `aois`, `parcels`, `features_parcels` (4).
**Sin RLS (justificado):** `rag_documents` (corpus global no multi-tenant), `schema_migrations` (interno dbmate).

> `features_parcels` con subquery `EXISTS` tiene coste; alternativa futura (US-053.x) = añadir columna
> denormalizada `session_id` por rollforward + trigger. Para el MVP la subquery es correcta y suficiente
> (volumen demo pequeño). Documentar como deuda.

### 2.1 Separación de roles (decisión pragmática MVP local)

- **La migración crea un rol de aplicación `agrosat_app`** (`NOLOGIN`/`LOGIN` según fase, `NOSUPERUSER NOBYPASSRLS`)
  con `GRANT SELECT/INSERT/UPDATE/DELETE` sobre las 4 tablas multi-tenant + `rag_documents` (read) + `USAGE` en
  secuencias.
- **Rol de migración = `agrosat` (superuser del compose) tiene BYPASSRLS implícito** → cumple "el rol de migración
  sí bypassa". No se crea un rol de migración separado: `agrosat` ya lo es. La separación queda: `agrosat`
  (migración, bypassa) vs `agrosat_app` (aplicación, NO bypassa).
- **En dev local pragmático**: el backend/agente **puede** seguir conectándose como `agrosat` para no romper el
  compose, PERO el **test de aislamiento se conecta explícitamente como `agrosat_app`** (única forma de que RLS
  sea observable, dado que superuser bypassa). Se documenta que en staging/prod la app DEBE usar `agrosat_app`
  (o el rol cloud equivalente sin BYPASSRLS). El listener funciona idéntico con ambos roles (emite `SET LOCAL`);
  solo cambia si la RLS se *enforce* o se *bypassa*.
- La migración setea `agrosat_app` password vía variable de entorno documentada, **nunca hardcodeada** (en dev
  un password fijo de compose es aceptable; en prod via Secret Manager). MVP: `agrosat_app` con password
  `agrosat_app` solo-local, documentado como dev-only.

## 3. Archivos exactos a crear / modificar

### Crear

1. **`db/migrations/<timestamp>_rls_multi_tenant.sql`** — vía `make db-new name=rls_multi_tenant` (genera el
   timestamp). Bloques `migrate:up` / `migrate:down`. Contenido up:
   - `CREATE ROLE agrosat_app NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE LOGIN PASSWORD 'agrosat_app';`
     (idempotente vía `DO $$ … IF NOT EXISTS … $$`).
   - `GRANT SELECT, INSERT, UPDATE, DELETE ON chat_sessions, aois, parcels, features_parcels TO agrosat_app;`
     `GRANT SELECT ON rag_documents TO agrosat_app;` `GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO agrosat_app;`

   - `CREATE POLICY tenant_isolation ON <tabla> FOR ALL USING (<expr>) WITH CHECK (<expr>);` (una policy `FOR ALL`
     cubre SELECT/INSERT/UPDATE/DELETE; `USING` filtra lectura/update/delete, `WITH CHECK` filtra insert/update).
   - `down`: `DROP POLICY IF EXISTS tenant_isolation ON <tabla>;` `ALTER TABLE … NO FORCE / DISABLE ROW LEVEL SECURITY;`
     revocar grants; `DROP ROLE IF EXISTS agrosat_app;`.

## 4. Interfaces públicas (firmas)

```python
# backend/app/core/db.py
async def get_pool() -> asyncpg.Pool: ...
async def close_pool() -> None: ...

@asynccontextmanager
async def session_scoped_conn(session_id: UUID) -> AsyncIterator[asyncpg.Connection]:
    """Acquire a backend pool connection with app.current_session primed.

    Emits, inside a transaction:
        SELECT set_config('app.current_session', $1, true)   -- SET LOCAL semantics
    bound to str(session_id). Identical contract to ml.agent.db.session_scoped_conn
    so the RLS policies apply uniformly whichever layer touches the DB.
    """

# Dependency wired by US-052/053 routers (declared here, consumed downstream):
async def get_request_session_id(request: Request) -> UUID: ...
async def get_scoped_conn(
    session_id: UUID = Depends(get_request_session_id),
) -> AsyncIterator[asyncpg.Connection]: ...
```

**Cómo lo invoca el pool por request:** cada router de negocio (US-052/053) declara
`conn: Annotated[asyncpg.Connection, Depends(get_scoped_conn)]`; la dependency hace
`async with session_scoped_conn(session_id) as conn: yield conn`, de modo que el `SET LOCAL` vive en la
transacción del request y la RLS aplica a todas las queries que el handler ejecute con `conn`.

## 6. Plan de tests

### 6.1 `tests/db/test_rls_isolation.py` (testcontainers, integración)

Patrón espejo de `test_migrations_rag.py` (auto-skip sin Docker). Setup: levanta PostGIS+pgvector, aplica TODAS
las migraciones como superuser, luego:

1. **Seed cross-session** (como superuser `test`): crea sesión A y sesión B, una AOI/parcel por cada una.
2. **Reconecta como `agrosat_app`** (rol no-superuser creado por la migración) — *imprescindible*: superuser
   bypassa RLS y el test sería falso verde.
3. Casos (con `SET app.current_session = '<A>'` por transacción):
   - **SELECT**: `SELECT count(*) FROM aois` → solo filas de A (no las de B). Idem `parcels`, `chat_sessions`,
     `features_parcels` (vía subquery).
   - **INSERT WITH CHECK**: insertar AOI con `session_id = B` estando seteado A → falla con
     `new row violates row-level security policy` (ERRCODE 42501).
   - **UPDATE**: `UPDATE aois SET label='x' WHERE session_id='<B>'` estando en A → 0 filas afectadas.
   - **DELETE**: `DELETE FROM parcels WHERE session_id='<B>'` estando en A → 0 filas afectadas; las de B siguen.
   - **Sin sesión seteada** (`missing_ok`): `SELECT count(*) FROM aois` sin `SET` → 0 filas (fail-closed), sin
     error.
4. **Rollback**: aplicar bloque `down`, verificar `pg_policies` vacío para esas tablas y `relrowsecurity=f`;
   round-trip `down → up` verde.
5. **Sanity superuser**: como superuser, con A seteado, `SELECT count(*) FROM aois` ve TODO (confirma que el
   bypass es real y por eso el test usa `agrosat_app`).

### 6.2 `test_db_session_listener.py` (unit, FakeConn)

Verifica que `backend.app.core.db.session_scoped_conn` emite `set_config('app.current_session', $1, true)` con el
sid bound y que el contrato es idéntico al de `ml/agent/db.py` (mismo string SQL).

### 6.3 Gates

- `make db-migrate` aplica limpio en docker-compose local; `make db-rollback` revierte.
- `make check` (lint backend + ruff) limpio sobre `backend/app/core/db.py`.

## 7. Riesgos + mitigaciones

| ID | Riesgo | Mitigación |
|----|--------|------------|
| R1 | **Superuser bypassa RLS** → test falso verde si corre como `agrosat`. (Confirmado en Context7 `rls.c`). | El test de aislamiento se conecta **explícitamente como `agrosat_app` (no superuser)**; caso de sanity que demuestra el bypass del superuser. |
| R2 | **`FORCE RLS` rompe queries del propio agente** si no setea la sesión (devuelve 0 filas inesperadas). | `current_setting('app.current_session', true)` con `missing_ok=true` → no lanza error; fail-closed (0 filas) en vez de excepción. El agente ya emite `SET LOCAL` (`ml/agent/db.py`); documentar que toda conexión app debe setearla. |
| R3 | **`parcels.session_id` es nullable** → filas legacy con NULL quedan invisibles a todos. | Aceptable para MVP (el seed siembra con sesión). Documentar; deuda: backfill + `NOT NULL` en rollforward futuro. |
| R4 | **`features_parcels` sin `session_id`** → subquery `EXISTS` costosa. | Subquery correcta y suficiente en volumen demo; deuda documentada: columna denormalizada + trigger en US futura. |
| R5 | **Romper el compose** si la app deja de conectarse como `agrosat`. | El rol `agrosat_app` se **añade** sin quitar `agrosat`; dev local puede seguir con `agrosat`. Solo el test usa `agrosat_app`. `APP_DATABASE_URL` default apunta a `agrosat_app` pero el cambio del DSN del backend a app-role es opcional en dev. |
| R6 | **Inconsistencia con el listener del agente** (dos contratos `set_config`). | El backend reusa el **mismo** string SQL y key `app.current_session`; test que lo fija. DRY: considerar helper compartido. |
| R7 | **dbmate envuelve cada migración en transacción** → `CREATE ROLE` + RLS OK en una transacción; pero `DROP ROLE` en down falla si hay objetos owned. | Revocar todos los grants antes de `DROP ROLE` en el bloque down; usar `DROP ROLE IF EXISTS`. Probar round-trip en testcontainers. |
| R8 | **Migración falla → data leak** (riesgo del plan §11). | Test en docker-compose local **antes** de cualquier deploy/endpoint (AC bloqueante); `make db-migrate` + `make db-rollback` verificados; CI corre `tests/db/test_rls_isolation.py`. |

## 8. Mapeo a rúbrica Avance 6 (seguridad / multi-tenant)

- **Seguridad / aislamiento multi-tenant**: RLS PostgreSQL por `session_id` aplicado vía migración versionada
  (dbmate), con separación de roles (app sin BYPASSRLS / migración con BYPASSRLS) y test de aislamiento
  cross-session (SELECT/INSERT/UPDATE/DELETE) verde como rol no-superuser. Evidencia directa del control de
  acceso a nivel de datos exigido por la rúbrica de despliegue MVP.
- **Reproducibilidad / IaC de datos**: migración rollforward reversible (up/down probado), sin
  `metadata.create_all`, sin tocar migraciones aplicadas.
- **Defensa en profundidad**: RLS (capa DB) + filtro `WHERE session_id` en cada tool (capa app, ya presente en
  `ml/agent/tools/`) — doble control.
- Cross-link: `agrosat-security` (RLS por session_id) + `agrosat-security-audit` (cross-session isolation tests)
  + `agrosat-db-migrations` (dbmate RLS).
