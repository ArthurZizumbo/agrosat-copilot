## (Referencia) Via vLLM — BLOQUEADA por el host
**Estado:** CODIGO done; EJECUCION BLOQUEADA (infra del host, no del codigo)
**Rama:** `feature/E7-US-048-qwen-vllm-serving`

## Resumen

Codigo de serving on-prem del reasoner Qwen MoE-A3B GPTQ-Int4 con vLLM, listo y
verificado en sintaxis + logica testeable. La EJECUCION en la VM H100 esta
bloqueada por la infraestructura del host (no por el codigo).

## Bloqueo de ejecucion (documentado)

vLLM requiere Linux; la VM H100 es Windows; su unica via Linux (WSL2) NO arranca
porque la VM es un guest Hyper-V SIN virtualizacion anidada expuesta
(`HCS_E_HYPERV_NOT_INSTALLED`, `VMMonitorModeExtensions=False`). Misma causa raiz
que el fallo de Docker. **Desbloqueo:** el sponsor/admin del host debe correr
`Set-VMProcessor -ExposeVirtualizationExtensions $true` sobre la VM apagada.
Detalle completo en [docs/serving/qwen35.md](../serving/qwen35.md). Artefacto
dejado en la VM: `F:\wsl\ubuntu-base.tar` (rootfs base para re-import inmediato).

## Sustitucion de modelo (verificada)

El id del plan `Qwen3.5-35B-A3B-GPTQ-Int4` **no existe en HF**. Real mas cercano:
**`Qwen/Qwen3-30B-A3B-Instruct-2507-GPTQ-Int4`** (MoE 30B/3B, Apache 2.0). La
sustitucion 35B -> 30B-A3B se ratifica en ADR-009 (US-050).

## Para ejecutar cuando se desbloquee

1. (host) habilitar nested virt -> (VM) `wsl --import AgrosatGPU F:\wsl\AgrosatGPU F:\wsl\ubuntu-base.tar --version 2`.
2. En WSL2: instalar CUDA + vLLM; `poetry run python scripts/download_qwen35.py`.
3. `bash scripts/serve_qwen35.sh` -> health OK -> `poetry run python scripts/benchmark_qwen35.py`.
4. Verificar p50<2s/p95<5s simple; registrar en MLflow.
