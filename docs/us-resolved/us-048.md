## Resumen ejecutivo

US-048 sirve el reasoner Qwen MoE-A3B on-prem en la H100. La via planeada (vLLM) quedo
**BLOQUEADA por la infraestructura del host** (la VM Windows es guest Hyper-V sin virtualizacion
anidada -> WSL2 no arranca, `HCS_E_HYPERV_NOT_INSTALLED`; misma causa que Docker), NO por el
codigo. Se SUSTITUYO por **llama.cpp nativo Windows + CUDA** con `llama-server.exe`, endpoint
OpenAI-compatible :8002, served-model `qwen35`, de modo que el `VLLMOpenAIBackend` del agente
(US-047) funciona SIN cambios. Se probo end-to-end en la H100 (15-jun-2026): modelo de 18.56GB
cargado (21.314 MiB VRAM), `/health`=200, smoke real coherente en espanol, ~24.8 tok/s, latencias
calientes que cumplen p50<2s / p95<5s. El id del plan `Qwen3.5-35B-A3B` no existe -> se usa el
real `Qwen3-30B-A3B-Instruct-2507` (Apache 2.0), ratificado en ADR-009/ADR-011.

## Decisiones tecnicas clave + caveats

- **Via vLLM bloqueada por infra del host** (nested-virt), NO por el codigo; el codigo vLLM esta
  completo (`scripts/serve_qwen35.sh`, `download_qwen35.py`, `benchmark_qwen35.py`) y listo para
  re-import (`F:\wsl\ubuntu-base.tar`) cuando el sponsor habilite nested-virt.
- **Gotcha CUDA**: build de llama.cpp debe ser <= CUDA del driver (driver 596.36 = CUDA 13.2;
  usar cuda-12.4, no 13.3). `--flash-attn` requiere valor `on`.
- **Qwen es text-only** (no multimodal) -> en US-049 evalua subset textual de AgroMind.
- **Endpoint default :8002** hardcoded (asume forward SSH local); overridable via
  `settings.vllm_qwen35_url`.
